# 项目列表加载修复（2026-09-08）

原页面先查列表，再为每个项目请求详情和完整展示结果，全部结束后才显示列表。
线上 15 个项目会触发 31 次列表、详情及结果请求，另外还有选中项目的状态请求。
实际读取发现两个项目的结果展开为 JSON 后约为 387 MB、199 MB，读取耗时分别约
5.11 秒、2.49 秒（不含后续展示整理、响应编码和网络传输）。列表查询本身约 13 毫秒。
这些大结果包含原始数据，以上大小不代表浏览器最终收到的压缩响应大小。

Redis 独立于应用容器，检查时连续运行约 39 天，仍有 363 个键。
列表、详情和结果的 TTL 分别为 30、120、300 秒；缓存过期会再次触发重读取。

修复后的项目管理页面直接使用列表中的摘要，只加载当前选中项目的详情。
完整结果在进入分析页面或执行原有分析流程时读取。
后续修复在数据库保存 `result_summary`（版本、可见结果数量、风险标志、可见键名），
随分析结果和人工复核结果在同一条 SQL 中更新。
列表据此恢复“需复核”“已完成”“处理中”“待分析”等原有状态区分。
状态仍遵循原页面规则，“已完成”并不意味着所有审查都无问题。
状态标签禁止收缩和换行，长项目名自行换行。

详情失败保留列表并提供重试；列表和详情超时为 20 秒。
技术标 OCR 范围只在对应阶段加载，加载完成前禁止修改或提交范围。
OCR 状态轮询在前一次请求完成后延迟继续，避免慢请求堆积。
切换项目时，旧详情响应不能覆盖当前项目。

后端配套修复 `PostgreSQLService.list_projects` 的关联计数：
`COUNT(*)` 改为 `COUNT(DISTINCT pd.id)`，避免文档连接放大组数。
已直接对照线上 15 个项目的详情核验，修正后的摘要数量全部一致。

## 验证

```sh
npm ci
npx playwright install --with-deps chromium
npm run lint
npm run test:loading
```

浏览器测试使用本地构建产物和模拟接口，不访问业务 API，覆盖：

- 详情挂起时，15 个项目摘要仍可见，且不会请求完整结果或未选中项目详情。
- 快速切换时丢弃旧项目的迟到响应。
- 详情失败后的重试与操作按钮恢复。
- 技术标剔除范围加载前的禁用及加载后的保留。
- 详情请求超时及慢 OCR 请求不堆积。
- 状态摘要区分风险、完成和待分析；1440/390 像素宽度下标签保持单行。
- 更新后不复用缺少摘要的旧版浏览器列表缓存。

后端部署前执行 `V20260908190000__add_project_result_summary.sql`，
部署后运行 `python -m tools.backfill_project_result_summaries --apply --verify-display`。
回填逐条核对真实展示逻辑，使用对象键及更新时间防止并发覆盖；
不修改报告或业务更新时间。线上全部 15 个项目已验证通过。

大型结果的存储结构和分析页面的结果处理没有在此次修改中重构；
本次解决的是列表打开时无条件读取所有项目结果造成的等待。
